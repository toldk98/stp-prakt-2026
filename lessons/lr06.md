## Мета

Налаштувати **власний віддалений репозиторій** кейсу та впевнено користуватися
робочими командами git на ньому.

## Кроки

1. Створити на GitHub власний репозиторій кейсу (наприклад
   `<прізвище>-powercalc`); `git remote add origin …`, `git push -u origin main`.
2. Перевірити `.gitignore`: виключено `.venv/`, `data/*.db`, `__pycache__/`,
   `report/`; **секретів і великих файлів в історії немає**.
3. Робота зі своїми гілками: створити `feature/<назва>`, зробити кілька
   комітів, злити в `main`.
4. Безпечні операції на власному репо: `amend` (виправити повідомлення),
   `revert` (відкат), `stash` (відкласти зміни), `restore` (скасувати правки).
5. Розібрати конфлікт на власному репо (злиття гілки, що змінює той самий файл).
6. Оформити `README.md` історії; за бажанням — тег версії (наприклад `v0.5`).
7. Пам'ятати правило спільного репо: внесок у репозиторій практик — **лише
   у своїй теці** `students/<прізвище>/`.

## Відмінність від ПР6

- **ПР6** — розв'язання конфліктів/merge у **спільному** репозиторії.
- **ЛР6** — налаштування remote та git-рутина на **власному** репозиторії.

## Артефакт

- власний репозиторій на GitHub із налаштованим `origin`;
- чиста історія: гілка, злиття, `amend`/`revert`/`stash` у логах;
- `README.md` із поясненням історії;
- посилання на remote у звіті `lr6/repo.md`.

## Критерії (5 балів)

| Складова | Бал |
| -------- | --- |
| Remote створено, `push` працює | 1.0 |
| `.gitignore` коректний, історія без сміття та секретів | 1.0 |
| Гілки та злиття використано свідомо | 1.0 |
| Продемонстровано `amend`/`revert`/`stash` | 1.0 |
| Конфлікт розв'язано на власному репо | 0.5 |
| README з історією та посиланням | 0.5 |

## Типові помилки

- закомічений `.venv/` або файл БД;
- секрет (пароль/токен) в історії — виправляти складно, краще не комітити;
- force-push без потреби;
- один коміт «all changes» замість осмисленої історії.
