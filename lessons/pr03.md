# ПР3. Функціональна та модульна декомпозиція

|                  |                                                    |
| ---------------- | -------------------------------------------------- |
| **Тривалість**   | 2 год                                              |
| **Форма**        | індивідуально, розбір у групі                      |
| **Блок**         | 3 — структура коду                                 |
| **Зв'язок**      | лекції 4, 7; продовжує ПР2; готує ЛР4–ЛР5          |
| **Оцінювання**   | 2.5 бала                                           |

## Мета

Розбити функції варіанта на **модулі з чіткими інтерфейсами** та перевірити
зв'язність архітектури (cohesion / coupling). Код не пишемо — проєктуємо.

## Кроки

1. Взяти декомпозицію з `pr1/design.md` і структури з `pr2/analysis.md`.
2. Згрупувати функції за **відповідальністю** в модулі, наприклад:
   `domain` (сутності), `analytics` (обчислення), `io` (читання/запис),
   `reporting` (звіти), `cli` (введення/виведення).
3. Для кожного модуля визначити **публічний інтерфейс**: що експортується,
   що лишається приватним (`_`-функції).
4. Визначити залежності між модулями й намалювати граф (хто кого імпортує);
   перевірити, що **немає циклів**.
5. Оцінити кожен модуль за **cohesion** (чи одна відповідальність) і
   **coupling** (скільки знає про інші); де треба — перегрупувати.
6. Зафіксувати угоди модулів: іменування, тип повернення, обробка помилок
   (виняток `PowerCalcDataError` із ЛР3).

## Артефакт

`students/<прізвище>/variant-NN/pr3/modules.md`:

- таблиця модулів: відповідальність | публічні функції | залежності;
- граф залежностей (гори, без циклів);
- аналіз cohesion/coupling кожного модуля;
- угоди (іменування, помилки, типи).

## Критерії (2.5 бала)

| Складова | Бал |
| -------- | --- |
| Модулі виділені за відповідальністю | 0.5 |
| Чіткі публічні інтерфейси | 0.5 |
| Коректний граф залежностей без циклів | 0.5 |
| Обґрунтований аналіз cohesion/coupling | 0.5 |
| Участь у розборі та захист рішень | 0.5 |

## Типові помилки

- модуль «utils» як смітник для всього;
- циклічні імпорти між модулями;
- публічні функції, які насправді деталь реалізації;
- змішування обчислень і виводу в одному модулі.
