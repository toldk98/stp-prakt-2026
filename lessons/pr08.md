# ПР8. Аналіз та тестування коду

|                  |                                                    |
| ---------------- | -------------------------------------------------- |
| **Тривалість**   | 2 год                                              |
| **Форма**        | індивідуально + взаємний code review               |
| **Блок**         | 7 — API та якість                                  |
| **Зв'язок**      | лекція 14; продовжує ПР7; готує ЛР8                |
| **Оцінювання**   | 2.5 бала                                           |

## Мета

Скласти **план тестування** свого варіанта, провести **code review** та
відпрацювати debugging. Це підготовка тестів для ЛР8.

## Кроки

1. Скласти план тестів для функцій та ендпоїнтів варіанта:
   - happy path;
   - крайові випадки (порожній вхід, нуль, межа ліміту);
   - негативні (некоректні дані, відсутній ресурс).
2. Визначити, що покривається **unit**-тестами, а що — **integration**.
3. Для кожного тесту описати: вхід | очікуваний результат | тип перевірки.
4. Визначити **фікстури та ізоляцію**: тимчасова БД, `tmp_path`, тестовий клієнт.
5. Провести **code review** фрагмента коду (свого або наданого): знайти
   помилки й «запахи» (див. ПР5), запропонувати виправлення.
6. Оформити **один приклад debugging**: відтворити помилку → локалізувати →
   виправити → додати **регресійний тест**.
7. Обговорити метрики якості: покриття, читабельність, назви тестів.

## Артефакт

`students/<прізвище>/variant-NN/pr8/`:

- `test-plan.md` — таблиця тест-кейсів (вхід | очікування | тип | unit/integration);
- `review.md` — результати code review (проблема | чому | як виправити);
- `debugging.md` — відтворення, причина, виправлення, регресійний тест.

## Критерії (2.5 бала)

| Складова | Бал |
| -------- | --- |
| Повний план тестів (3 категорії) | 0.5 |
| Коректний поділ unit/integration і фікстури | 0.5 |
| Змістовний code review із виправленнями | 0.5 |
| Debugging із регресійним тестом | 0.5 |
| Участь у взаємному review | 0.5 |

## Типові помилки

- тести лише на happy path;
- тест залежить від порядку запуску або реальних даних;
- назва тесту `test1` без сенсу;
- review у стилі «усе погано» без конкретних виправлень.
